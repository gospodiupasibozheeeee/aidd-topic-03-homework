#### 1.3. Ошибки и проблемы, возникавшие при работе с Antigravity

1. **Рассинхронизация контекста аутентификации в тестах:**
   - *Проявление:* тесты представлений `LoginRequiredMixin` в `APITestCase` падали с ошибкой `AssertionError: 302 != 200`.
   - *Причина:* метод `self.client.force_authenticate(user=self.user)` аутентифицирует пользователя только на уровне REST Framework, но не создает стандартную Django-сессию для обычных контроллеров.
   - *Решение:* агент самостоятельно диагностировал проблему и добавил парный вызов `self.client.force_login(self.user)`.
2. **Валидация внешнего ключа в сериализаторе:**
   - *Проявление:* `POST /api/v1/strategies/` возвращал статус `400 Bad Request`.
   - *Причина:* поле `portfolio` в `TradingStrategySerializer` не было объявлено в `read_only_fields`, хотя подставлялось в методе `perform_create` из контекста текущего пользователя.
   - *Решение:* агент оперативно отредактировал `serializer.py`, включив `portfolio` в `read_only_fields`.
3. **Отсутствие миграций перед первым запуском тестового раннера:**
   - *Проявление:* SQLite выдавал `OperationalError: no such table: dashboard_pricehistory`.
   - *Причина:* новые модели были добавлены в `models.py`, но команда `makemigrations` еще не была вызвана.
   - *Решение:* агент выполнил `makemigrations dashboard`, сгенерировал файл миграции `0009_...` и применил его к тестовой и основной базе.

### 3. Детальный разбор ключевых различий

#### 3.1. Архитектура виртуального портфеля
- **Реализация в Google Antigravity:**
  ```python
  # dashboard/services/portfolio_service.py
  @transaction.atomic
  def buy_share(portfolio, share, quantity, price=None):
      # Пессимистическая блокировка для защиты от race condition
      portfolio = Portfolio.objects.select_for_update().get(id=portfolio.id)
      total_amount = Decimal(quantity) * execution_price
      if portfolio.balance < total_amount:
          return None, "Недостаточно средств на балансе"
      portfolio.balance -= total_amount
      portfolio.save(update_fields=["balance"])
      # Пересчет средневзвешенной цены позиции
      ...
  ```
  *Оценка:* Реализована классическая финансовая архитектура торгового терминала. Полноценно моделируются денежные потоки, заморозка средств, проверка платежеспособности и расчет прибыли от закрытия позиции.

- **Реализация в DeepSeek:**
  Позиции и средняя цена рассчитываются агрегацией по истории сделок без проверки баланса денежных средств. Пользователь может «купить» виртуальных акций на миллиард долларов при любом состоянии счета.

#### 3.2. Наличие программного интерфейса (REST API)
- **Google Antigravity:** разработал 8 сериализаторов, 7 ViewSets и маршрутизатор DRF, зарегистрировавший маршруты:
  - `/api/v1/watchlist/`
  - `/api/v1/notifications/`, `/api/v1/notifications/mark-all-read/`
  - `/api/v1/portfolio/my/`, `/api/v1/portfolio/buy/`, `/api/v1/portfolio/sell/`
  - `/api/v1/transactions/`
  - `/api/v1/price-history/`, `/api/v1/shares/<pk>/dynamics/`

### 4. Ограничения агентов и проблемы в ходе эксплуатации

1. **Ограничения Google Antigravity:**
   - При генерации большого объема кода за один шаг (например, сериализаторы для 8 моделей) агент может допустить мелкие неточности в `read_only_fields` или параметрах валидации. Однако при запуске тестов агент мгновенно локализует и устраняет эти неточности.
   - Склонен следовать существующей структуре приложения (расширять текущий модуль), даже когда создание отдельного Django-приложения могло бы улучшить модульность.
2. **Ограничения DeepSeek:**
   - **Склонность к компромиссному упрощению требований (Scope Cutting):** столкнувшись с большим объемом задачи в Задании №4, агент предпочел опустить учет денежного баланса и реализацию REST API, честно зафиксировав это в ограничениях, но не выполнив требования на 100%.
   - Меньшая способность к многослойной интеграции (одновременная поддержка SSR + REST API).
