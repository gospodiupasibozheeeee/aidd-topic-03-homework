## 1. Назначение документа и границы

Документ фиксирует **фактически реализованное** поведение приложения Investing Demo:
какие действия доступны пользователю, какие ограничения и проверки действуют, какие
результаты возвращает система. Дефекты, неоднозначности и противоречия вынесены в
раздел 8 и **не рассматриваются как функциональные требования**.

В документе используются обозначения:

- `ФТ-xx` — функциональное требование;
- `БП-xx` — бизнес-правило/проверка/ограничение;
- `UC-xx` — пользовательский сценарий (use case);
- `Д-xx` — дефект, противоречие или неоднозначность.

Все требования имеют подтверждение в исходном коде (файл и строки). Если поведение
реализовано с дефектом, требование формулирует **наблюдаемое поведение**, а дефект
описывается отдельно в разделе 8.

### 1.1. Что входит в область требований

- публичный каталог акций и карточка акции с графиком;
- управление каталогом через HTML-формы;
- регистрация, вход и выход пользователя;
- REST API над каталогом (CRUD, фильтрация, сортировка, поиск, пагинация);
- администрирование каталога через Django admin;
- импорт справочника акций из Tinkoff Invest API;
- фоновое обновление последних цен через Celery;
- хранение данных в PostgreSQL и стандартная аутентификация Django.

### 1.2. Что не входит в область требований

В исходном коде **отсутствуют** следующие возможности, поэтому они не являются
восстановленными требованиями:

- персональные портфели, позиции, сделки и расчёт прибыли/убытка;
- персональные списки наблюдения, целевые цены и уведомления;
- сохранение истории рыночных цен в БД;
- симулятор инвестиционных стратегий;
- роли, владельцы акций, разграничение доступа к отдельным записям;
- брокерские операции, платежи, экспорт отчётов, API-документация, real-time/WebSocket.

Эти возможности перечислены как пробелы модели данных в разделе 8.4 и в
[ANALYSIS.md](ANALYSIS.md).

## 2. Роли и акторы

| Актор | Описание | Фактические права |
|---|---|---|
| Анонимный посетитель | Не прошедший аутентификацию пользователь | Просмотр каталога и карточки; регистрация; вход; REST API (фактически без ограничений) |
| Аутентифицированный пользователь | Пользователь со стандартной учётной записью `auth.User` | Всё, что доступно анонимно, плюс HTML-создание, редактирование и удаление акций |
| Администратор | Пользователь с `is_staff=True` | Управление `Share` через `/admin/`; остальные права — как у обычного пользователя |
| Оператор CLI | Пользователь с доступом к терминалу и настройкам | Запуск `manage.py`-команд, Celery Beat/Worker |
| REST-клиент | Внешняя программа, работающая с JSON API | CRUD-операции над акциями; фильтрация, сортировка, поиск, пагинация |
| Фоновый процесс | Celery Beat + Celery Worker | Периодическое обновление цен по расписанию |
| Внешняя система | Tinkoff Invest API | Источник справочника, свечей и последних цен |

**Важно:** в приложении нет владельцев акций и ролей, кроме стандартных флагов Django
(`is_staff`, `is_superuser`). Любой аутентифицированный пользователь может изменить или
удалить любую акцию через HTML-интерфейс; API вообще не требует аутентификации
(см. Д-01).

### 4.2. Детализированные сценарии

#### UC-01. Просмотр каталога акций

**Актор:** любой посетитель.

1. Пользователь открывает `/`.
2. `ShareListView` выбирает акции из БД с сортировкой по `name` и пагинацией по 100.
3. Шаблон `list.html` выводит таблицу: тикер (ссылка на карточку), название, ISIN,
   текущую цену с валютой, цветовую подсветку тренда.
4. Для аутентифицированного пользователя дополнительно выводятся кнопки
   «Редактировать»/«Удалить» и кнопка «Добавить».
5. При отсутствии записей выводится сообщение «Акций еще нет».
6. При наличии более 100 записей отображается пагинация.

**Постусловие:** страница каталога отображена; данные не изменены.

**Подтверждение:** `dashboard/views.py:20-26`, `dashboard/urls.py:14`,
`dashboard/templates/dashboard/list.html:9-84`.

#### UC-02. Просмотр карточки и графика

**Актор:** любой посетитель.

1. Пользователь открывает `/<pk>`.
2. `ShareDetailView` загружает акцию `Share.objects.get(id=pk)`.
3. Вызывается `get_graph(share)`: Tinkoff API запрашивает дневные свечи за последние
   180 дней; Plotly формирует HTML-фрагмент.
4. Шаблон `detail.html` выводит название, последнюю цену с валютой, время обновления и
   график.

**Исключение:** если `pk` не существует, `Share.DoesNotExist` не перехватывается —
возникает 500 (дефект Д-03); если Tinkoff API недоступен, страница также завершается
ошибкой (дефект Д-17).

**Постусловие:** страница карточки отображена; данные не изменены.

**Подтверждение:** `dashboard/views.py:29-38`, `dashboard/services/graph.py:11-36`,
`dashboard/templates/dashboard/detail.html:8-28`.

#### UC-03. Регистрация

**Актор:** анонимный посетитель.

1. GET `/userregistration/` — отображается форма с полями `email`, `password1`,
   `password2`.
2. Пользователь вводит e-mail и два пароля.
3. POST — `RegistrationForm.is_valid()`:
   - проверяется формат e-mail;
   - проверяется совпадение паролей;
   - проверяется отсутствие пользователя с таким e-mail.
4. При успехе `save()` создаёт `auth.User` с `username=email`, `email=email`,
   хеширует пароль, затем выполняется `login()` и редирект на `/`.
5. При ошибке форма перерисовывается с сообщением в `error`.

**Исключения:** при ошибке отдельного поля вместо `__all__` возможен `KeyError` (Д-04);
парольные валидаторы Django не применяются (Д-05).

**Подтверждение:** `user/views.py:36-55`, `user/forms.py:8-53`,
`user/templates/user/registration.html:3-24`.

#### UC-04. Вход

**Актор:** анонимный посетитель.

1. GET `/userlogin/` — форма с `email` и `password`.
2. POST — значения читаются из `request.POST`; вызывается
   `authenticate(username=email.lower(), password=password)`.
3. При успехе `login()` создаёт сессию и выполняется редирект на `/`.
4. При неудаче форма перерисовывается с сообщением
   «Неверный логин или пароль! Повторите попытку.».

**Исключения:** `is_valid()` не вызывается; отсутствие поля даёт 500 (Д-06); e-mail в
верхнем регистре не проходит аутентификацию (Д-07).

**Подтверждение:** `user/views.py:8-33`, `user/forms.py:56-69`.

#### UC-05. Выход

**Актор:** аутентифицированный пользователь.

1. Пользователь нажимает «Выход» в шапке.
2. GET `/userlogout/` вызывает `logout(request)`.
3. Выполняется редирект на `/`; сессия завершена.

**Подтверждение:** `user/views.py:58-64`, `dashboard/templates/dashboard/base.html:37-43`.

#### UC-06. Добавление акции через сайт

**Актор:** аутентифицированный пользователь.

1. На главной странице доступна кнопка «Добавить» (только для аутентифицированных).
2. GET `/create` — форма по всем редактируемым полям `Share`.
3. POST — форма валидируется (`figi`, `ticker`, `uid` уникальны; обязательные поля
   заполнены; соблюдены максимальные длины).
4. При успехе запись сохраняется, выполняется редирект на `/`.
5. При ошибках форма перерисовывается с ошибками полей (crispy).

**Исключение:** анонимный GET/POST перенаправляется на `/` (не 403).

**Подтверждение:** `dashboard/views.py:11-17,41-46`, `dashboard/forms.py:6-11`,
`dashboard/templates/dashboard/create.html:13-19`.

#### UC-07. Редактирование акции через сайт

**Актор:** аутентифицированный пользователь.

1. В строке акции нажать «Редактировать».
2. GET `/update/<pk>` — форма предзаполнена текущими значениями.
3. POST — изменения валидируются и сохраняются; редирект на `/`.
4. При отсутствии `pk` — 404 (generic view).

**Подтверждение:** `dashboard/views.py:49-55`, `dashboard/urls.py:17`.

#### UC-08. Удаление акции через сайт

**Актор:** аутентифицированный пользователь.

1. Нажать «Удалить» в строке акции.
2. GET `/delete/<pk>` — страница подтверждения с названием акции.
3. POST — запись удаляется; редирект на `/`.

**Подтверждение:** `dashboard/views.py:58-63`,
`dashboard/templates/dashboard/delete.html:9-13`.

#### UC-09. Просмотр списка через API

**Актор:** REST-клиент.

1. GET `/api/v1/shares/`.
2. `ShareViewSet` применяет фильтры, сортировку, поиск и пагинацию.
3. Возвращается JSON `{count, next, previous, results}`; по умолчанию 100 записей.
4. Поддерживаются параметры `name`, `ticker`, `ordering`, `search`, `limit`, `offset`.

**Подтверждение:** `dashboard/api/v1/views.py:10-22`,
`dashboard/api/v1/serializer.py:6-19`, `config/settings.py:31-35`.

#### UC-10. Создание/изменение/удаление через API

**Актор:** REST-клиент.

1. POST `/api/v1/shares/` — создание по полям сериализатора; 201.
2. PUT/PATCH `/api/v1/shares/<pk>/` — полное/частичное обновление; 200.
3. DELETE `/api/v1/shares/<pk>/` — удаление; 204.
4. Отсутствующая запись — 404; невалидные данные — 400.

**Ограничение:** `uid` не входит в сериализатор, поэтому создание через API имеет
дефект уникальности (Д-02); анонимный доступ не ограничен (Д-01).

**Подтверждение:** `dashboard/api/v1/serializer.py:6-19`,
`dashboard/api/v1/router.py:5-6`.

#### UC-11. Управление в admin

**Актор:** администратор (`is_staff=True`).

1. Открыть `/admin/`, войти.
2. В разделе «Акции» доступны список, поиск и редактирование `Share`.
3. Поля формы админки: `figi`, `isin`, `name`, `ticker`, `currency`, `uid`,
   `last_price`, `is_trend_high`; `updated_at` не редактируется.

**Подтверждение:** `dashboard/admin.py:6-19`.

#### UC-12. Импорт справочника

**Актор:** оператор CLI.

1. Выполнить `python manage.py add_shares`.
2. Команда открывает Tinkoff `Client`, получает `client.instruments.shares()`.
3. Для каждого инструмента вызывает `Share.objects.get_or_create(...)` по всем полям.
4. Новые записи добавляются; точные совпадения не дублируются.

**Ограничение:** существующие записи не обновляются; при изменении названия/валюты
возможна ошибка уникальности (Д-10).

**Подтверждение:** `dashboard/management/commands/add_shares.py:11-22`.

#### UC-13. Фоновое обновление цен

**Актор:** Celery Beat/Worker.

1. Beat каждые 10 секунд публикует задачу `dashboard.tasks.update_last_price`.
2. Worker получает задачу и читает все акции.
3. Для каждой акции вызывает `get_last_data(share)`, получает последнюю цену.
4. Сравнивает с сохранённой ценой и выставляет `is_trend_high`.
5. Обновляет `last_price` и `is_trend_high` в БД.
6. Ошибки по отдельной акции логируются, цикл продолжается.

**Ограничения:** N+1 запросов, отсутствие блокировки и обновления `updated_at`
(Д-08, Д-09); см. раздел 8.

**Подтверждение:** `config/celery.py:13-18`, `dashboard/tasks.py:7-28`,
`dashboard/services/market_data.py:6-11`.

## 9. Выводы

1. Приложение реализует **публичный каталог акций** с карточкой, графиком за 180 дней,
   HTML-CRUD для аутентифицированных пользователей, REST CRUD, регистрацию/вход/выход,
   admin, импорт справочника и фоновое обновление цен.

2. Функциональные требования сгруппированы в **45 ФТ**: каталог и карточка (ФТ-01…08),
   HTML-управление (ФТ-09…15), аутентификация (ФТ-16…24), REST API (ФТ-25…34),
   администрирование (ФТ-35…36), импорт/фон (ФТ-37…41), сквозные (ФТ-42…45).

3. Ключевые бизнес-правила: пагинация 100 и сортировка по `name`; уникальность
   `figi`/`ticker`/`uid`; доступ к HTML-изменению только после входа; регистрация по
   e-mail с автоматическим входом; API с фильтрами/сортировкой/поиском/пагинацией;
   фоновая задача каждые 10 секунд.

4. Требования подтверждены кодом, но часть поведения реализована с дефектами:
   открытый API, `uid` вне сериализатора, 500 на отсутствующей карточке, `KeyError` в
   регистрации, отсутствие обновления `updated_at`, N+1 в фоне, потеря точности цен.

5. В модели данных есть только `Share` и стандартная `User`; отсутствуют портфели,
   сделки, watchlist, история цен и стратегии. Это ограничивает текущие требования
   каталогом и не позволяет считать реализованными сценарии задания №4.

6. Для задания №3 приоритетными являются: закрытие API правами доступа, исправление
   `uid`, замена `FloatField` на `DecimalField`, обработка ошибок Tinkoff, исправление
   валидации форм, обновление `updated_at`, устранение N+1 и настройка конфигурации.
